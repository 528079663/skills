# 人设档案 Schema + 提取规则（优化版）

本文件同时是 **profile 存储结构规范** 和 **提取规则手册**。提取人设 / 行文风格时，
严格按本文件执行——尤其涉及「频率 / 密度」的字段，**必须先量化再断言**，禁止凭印象归纳。

> 核心纪律：writing_craft 里任何含「高频 / 稀疏 / 每卡 / 每点」等频率字眼的字段，**必须先统计源文真实分布（出现次数 / 覆盖篇数）并把数字写进依据**，再下结论；禁止凭肉眼扫几篇就断言"是固有特征"（此前"案例焊死每点 / 每卡"即源于此）。

---

## 0. 提取总流程（执行顺序，必须遵守）

1. **逐篇处理**：素材分类（§1）→ 正文提取 / OCR（§2）→ 存下每篇纯文本（标注篇号）。
2. **合并分析**：把所有纯文本合并，做分词、句式、标题等结构化统计。
3. **跨篇综合**：按 §4（人设维度）+ §5（writing_craft）提取，遵守 §3 证据要求；
   涉及频率的一律按 §6 量化。
4. **专名占位**：按 §7 把写作手法示例里的专名替换为占位符，校验每个字段都有证据支撑。
5. **组织落库**：按下方 profile 结构（嵌套、分内容模式）组织，经 persona_manager.py 落库。

---

## 1. 素材预处理与智能分类

用 BeautifulSoup 定位正文容器（优先级 `#js_content` > `article` > `body`），清洗后统计三指标：

- **`text_len`**：所有 `<p>` 标签内纯文本长度（汉字 + 数字 + 有意义标点，去除空白）。（注：此 `text_len` 仅用于 §1 内容类型分类、含标点；写作字数约束 `length_profile.per_item_chars` 的『字』指**汉字字符数、不含标点**，定义见 `writing_rules_dual_version.md` 第 27 行注，两处口径不同，别混用。）
- **`img_count`**：正文容器内 `<img>` 标签数量。
- **`p_count`**：正文容器内 `<p>` 标签数量。

**分类决策（满足任一即归类）：**

> ⚠️ **自动化判定权威来源**：实际走脚本时，判定以 `scripts/preprocess_html.py` 的
> `classify(para_count, img_count)` 为准——`para_count < 3 且 img_count >= 2` → 「图片贴图」，
> 否则「图文文章」。下方手工人判阈值**必须与该函式对齐**，二者不得分叉。

| 类型 | 判定条件 | 处理 |
|---|---|---|
| **图片贴图** | `p_count < 3` 且 `img_count ≥ 2` | 走 OCR（§2） |
| **图文文章** | `p_count ≥ 3` 或 `img_count < 2`（即"非贴图"） | 直接解析 `<p>` |
| **短图文** | `p_count ≥ 3` 但 `text_len < 200`（正文极短） | 按图文文章处理，字段注明「短文本」 |
| **边界情况** | 以上都不明确 | 默认归**图文文章**，避免误判而跳过内容 |

> 旧经验值「数 `<p[ >]`：贴图 ≈2 / 文章 ≥27」是本项目实测的快速参考，仍可辅助判断，
> 但**以 `classify()` 与上方阈值（p_count / img_count）为准**。切勿用「`<p>` 内直接含中文」判定（文章 `<p>` 多嵌套 `<span>/<strong>`，会误报）。

## 2. 正文获取与 OCR 去噪

**图文文章**：提取所有 `<p>` 纯文本，保留段落换行，丢弃 script / style / 注释；
段落内 `<img>` 若无 `alt` 文本则跳过该图。

**图片贴图**：
1. 按文档序对所有图片调用**全局 OCR 微服务**（集群 / 单机两版、端口统一，用法见 `~/.workbuddy/ocr-microservice.md`）；或对本地 HTML 用 `extract_article.py <文件.html> --with-images --ocr-images`（本地文件必须显式 `--ocr-images` 才会跑 OCR，否则只列图链）。
2. **去噪规则（顺序执行）**：
   - 丢弃长度 ≤1 的行；
   - 丢弃仅含数字 / 符号 / 乱码（如 `#@¥`）、无实际语义的行；
   - 丢弃常见水印模板：含「长按识别」「扫码关注」「查看原文」等的行，除非它们成句出现在正文中；
   - 合并相邻且语义连续的短句，形成完整段落。
3. 过滤后按图片顺序拼接，每张图前加标记 `【图1】`、`【图2】`……某图全部被过滤则标 `【图X：无有效文字】`。
4. 拼接结果视为该篇素材的「正文文本」，供后续分析。

**关键原则**：OCR 得出的文字**除非能形成语义完整的句子，否则一律当噪声忽略**，
不得写入人设或写作手法。（贴图封面常为艺术字，数字易被 OCR 误识，如「8个」→「78个」，
封面编号须人工核对。）

---

## 3. 多篇素材综合与证据要求（素材 ≥2 篇时）

- **共性优先**：提取的人设特征 / 写作模式，必须至少在 **2 篇** 中有明确表现，方可列为「核心特征」。
- **孤例降级**：仅在单篇出现的特征，归入「偶发特征」或在该维度备注「仅见于篇X」，不得纳入主要描述。
- **证据溯源**：每个结论后括注来源篇目（如「篇1、篇3」），方便校验。

## 3.5 领域与成文转换角色（domain / author_mapping，重要）

提取到的人设只提供「风格层 + 骨架层」，其 `identity.brand_name / baby_name / self_refer` 是**源作者**的专名（别人的）。
实际成文必须映射到**用户自己的身份**，由人设顶层两个字段承载（与 `profile` 同级，persona_manager.py 透传存储）：

- **`domain`**：领域标签（字符串），按素材主题判定，如 `母婴`、`美食`、`职场`、`科技`、`理财` 等。
- **`author_mapping`**：用户成文身份映射对象（对象，可空）：
  ```json
  {
    "resolved": true,
    "sign_name": "署名 / 品牌名（如 福宝妈妈）",
    "signoff": "结尾落款（如 福宝妈妈育儿笔记）",
    "self_refer": "作者自称（如 小琳 / 福宝妈妈）",
    "baby_name": "宝宝小名（母婴领域填；其他领域可空字符串）",
    "note": "映射说明（可选）"
  }
  ```
  > **母婴领域捷径（变量源，禁止写死）**：`domain=母婴` 的人设，`author_mapping` **不写上述字面字段**，
  > 只写 `{"ip_key": "福宝妈妈", "resolved": true}`；真实身份值（`sign_name`/`signoff`/`self_refer`/`baby_name`）
  > 由 `references/ip_identity.json` 这一 **单一事实来源** 在 `persona_manager` 的 `view`/`export` 时解析展开，
  > 改落款/署名/自称只改 `ip_identity.json` 一处。非母婴人设仍按上面字面字段内联存储。

**判定与填充规则**：
1. **母婴领域（`domain=母婴`，变量源，禁止写死）**：`author_mapping` **只存引用**
   `{"ip_key": "福宝妈妈", "resolved": true}`，真实身份值（`sign_name`/`signoff`/`self_refer`/`baby_name`）以
   `references/ip_identity.json` 的 **单一事实来源** 为准，由 `persona_manager` 在 `view`/`export` 时解析展开；
   **禁止在 persona 内写死身份副本**。改落款/署名/自称只改 `ip_identity.json` 一处。
   依据见用户级 `~/.workbuddy/MEMORY.md` 的「内容创作 IP 约定」。提取/新建母婴人设时直接填 `ip_key`，无需询问。
2. **其他领域（`domain≠母婴`）**：首次用该人设创作内容前，skill 必须先用 `AskUserQuestion` 向用户确认
   其成文身份（署名 / 落款 / 自称 / 领域专属元素如宝宝名），确定后 `update` 写入 `author_mapping`
   并置 `resolved=true`，后续复用不再询问。
3. **成文替换纪律**：`identity.brand_name / baby_name / self_refer` 是源作者专名，**成文时一律用
   `author_mapping` 覆盖**，绝不保留源作者品牌名（如饭饭妈、九龄）。

## 4. 人设维度提取规范（逐维度观察点 + 输出格式）

严格按下表执行，不可凭空发散。缺失项填空字符串 / 空数组 / `null`，**禁止生造**。

| 维度 | 提取方法（观察点） | 输出要求 |
|---|---|---|
| **身份 / 领域** | ① 作者自称（如「做了十年 HR 的妈妈」）② 高频领域术语（辅食、绘本、感统）③ 引用的经历场景（办公室、幼儿园） | 简短短语，如「育儿博主，前外企 HR」；无法判断填「不详」。 |
| **语调 / 口吻** | 计算三指标：· 第二人称「你 / 你们」句子比例（≥15% 为强对话感）· 感叹 / 语气词密度（啊、啦、呢、哦）· 主观评判形容词（踩雷、智商税、真的服了）。归类为 ①亲切唠嗑式 ②冷静理性式 ③犀利毒舌式 ④温暖治愈式 | 选一个主导风格 + 一句理由（如「密集使用『咱们』『对不对』，属唠嗑式」）。 |
| **句式特征** | 抽样每篇前 / 中 / 后各 200 字，统计：· 短句（≤15 字）占比 · 问句（？结尾）比例 · 排比句次数（如「不…不…不…」） | 描述，如「短句为主（约 70%），频繁设问，偶用排比」。 |
| **高频用词** | 合并所有正文，jieba 分词 → 去停用词 → 取频次前 20；再筛出**有辨识度**的 ≤10 个（如「娃、绘本、共情、避雷、亲测」），剔除通用词。 | 列表，如 `["娃","共情","实测","踩坑","干货"]`。 |
| **修辞习惯** | 识别并计数：· 比喻 / 类比（「像…一样」）· 对比 / 反差（「不是…而是…」）· 夸张（「一万个」「爆炸」「封神」）· 举例（「比如」「就拿我家来说」） | 描述 + 典型短引文（≤15 字）。如「爱用对比，『不是吓唬你，是真管用』」。 |
| **价值观 / 立场** | 抽取观点性句子（建议 / 判断 / 总结句），合并近义，提炼 3–5 条价值关键词。 | 列表，如 `["拒绝焦虑育儿","重视自主阅读","反对超前教育"]`，**必须有原文依据**。 |
| **禁忌 / 规避** | 观察是否出现脏话、过度情绪化、贬低性称呼、争议话题；若无，按克制程度推断。 | 短语，如「避免情绪宣泄和贬低他人」；无明确特征填「无明显禁忌」。 |

## 行文工艺字段（writing_craft）

仅有 `identity / style` 不足以高效产出内容——还要知道「这篇文章怎么搭出来的」：结构骨架、
开头钩子、标题公式、品牌支招框、段落节奏、排版、论证、字数画像。这些定义「怎么写」，
每次创作都应**复用**（区别于 `samples` / `examples` 仅供体会的例句）。

`writing_craft` 置于 `profile` 内，随人设持久化（persona_manager.py 对 profile 整段存储、深层合并）。

```json
{
  "writing_craft": {
    "structure_template": {
      "description": "标准文章骨架（模块典型顺序，可选模块标 （可选））",
      "modules": ["痛点 / 场景引入", "分点展开（N 个 X）", "个人案例（可选）", "品牌支招框", "总结金句 / 互动引导"]
    },
    "opening_hooks": [
      {"type": "提问式", "example": "『孩子一输就哭，怎么劝都没用，你是不是也头大？』"},
      {"type": "痛点直击式", "example": "『说了 800 遍别摸插座，娃偏要摸，肺都要气炸』"}
    ],
    "closing_patterns": ["PS 一句互动收尾", "鼓励式金句"],
    "title_formulas": [
      {"pattern": "数字 + 痛点 + 解决方案", "examples": ["《{baby_name}爱打人？这 3 招比说教管用》"]},

    "signature_boxes": [

    "paragraph_rhythm": "短段落，平均 2-3 行 / 段，段间空行，每千字约 N 个 emoji，小标题用『❶❷❸』",
    "layout": {"emoji_density": "每千字 X 个", "dividers": "空行分段 / 分隔线", "subhead_style": "纯文字加粗 / 数字编号 / emoji+文字", "image_habit": "封面 + 文中插图，图文比例"},

    "examples": [
      {"usage": "支招框示范（仅体会格式，禁止原样复制；专名用占位符）", "snippet": "『💡{brand_name}支招：室温合适就放心让娃踩地。』"}
    ]
```

### 5. writing_craft 提取规范（逐项执行；先分块再跨篇归纳）

- **5.1 结构骨架**：为每篇打模块标签（可选标签：引入钩子 / 痛点描述 / 观点提出 / 分点展开 /
  案例插入 / 支招建议 / 总结升华 / 互动引导 / 推广植入）。统计各篇模块序列的**共同路径**，
  输出一个典型流程，不总出现的模块标 `（可选）`。
- **5.2 开头钩子**：把每篇开头 1-2 段归类（提问式 / 故事场景式 / 颠覆常识式 / 数据引入式 /
  直击痛点式），取出现最多的 2~3 类，各附一句真实开头缩略（≤30 字）；专名用 `{baby_name}` 占位。
- **5.3 标题公式**：提取所有标题 → 去无关符号 → 归纳共性套路，附公式描述 + 2~3 个真实标题（专名占位）。
- **5.4 品牌支招框**：找反复出现、格式固定的建议区块（固定图标 / 边框 / 名称）；
  记录名称、符号、通常位置；不存在则记「无固定支招框」。
- **5.5 段落节奏 / 排版**：平均段落字数、是否空行、emoji 频率（个 / 千字）、小标题样式。
- **5.6 论证模式**：标注论据类型（个人经验 / 科学文献 / 专家意见 / 网络数据 / 读者留言 / 书籍引用）
  及占比，输出主要模式并括注篇号。
- **5.7 字数画像**：清单型每点平均字数（汉字）、单篇总字数区间。

## 6. 频率与密度量化标准（★ 防密度漂移的硬规则）

对特定元素（如自家娃案例、互动提问、品牌支招框）做频率统计，**必须先跑计数**，用统一表述：

| 档位 | 判据 | 表述示例 |
|---|---|---|
| **高频** | 在 **≥70%** 素材中出现且次数多 | 「高频使用（4/5 篇）」 |
| **偶尔** | 在 **30%~70%** 素材中出现 | 「偶尔使用（2/5 篇）」 |
| **稀疏** | 在 **<30%** 素材中出现 | 「稀疏使用（1/5 篇）」 |
| **无** | 0% | 「未出现」 |

- 统计结果写入 `content_modes[类型].frequency_notes`（结构见下）；**禁止**用「固有特征」「每卡都有」
  这类未经计数的定性断言。
- 典型要统计的元素：`baby_case`（自家娃案例 / 专名出现的卡片或要点占比）、`interaction_guide`
  （互动提问 / 引导收藏）、`brand_box`（支招框出现率）等。

```json
{
  "frequency_notes": {
    "baby_case": "稀疏使用（1/5 篇）",
    "interaction_guide": "高频使用（4/5 篇）",
    "_evidence": "计数依据：想想跨 6 篇每卡占比 0/8 ~ 6/8，通用『宝宝』为主"
  }

```

## 7. 命名一致性处理（占位符）

1. 提取**写作手法**（writing_craft 的所有示例、标题示例、钩子示例）时，自动识别专名并替换为占位符：
   - 宝宝小名 / 昵称 → `{baby_name}`
   - 品牌名 / 笔名（如「福宝妈妈」「奶爸小强」）→ `{brand_name}`
   - 特定自称（如「老母亲」「本宫」）→ `{self_refer}`
2. **识别方法**：结合高频人名、称呼上下文（「我家 XX」「XX 妈妈」）、文首 / 文末署名。
3. writing_craft 里一律用占位符；**真实名称单独保存**在 `identity.brand_name / baby_name / self_refer`
   与人设 `name`，不做替换。生成内容时把占位符回填为人设品牌名（如 `{baby_name}` → 福宝）。
4. 常见冲突：来源作者真名（如「想想」）与人设品牌名（如「福宝」）不同——**结构可复用，生成时统一
   回填人设品牌**，不因来源作者而异。

## 内容类型（content_modes）：图文文章 / 图片贴图

同一套人设的素材往往混有两种写作内容，**必须分开建模**，否则生成保真度会漂移：

- **图文文章（`图文文章`）**：正文在 `<p>`/`<section>` 文字里，可直接解析。writing_craft 描述
  散文清单骨架（结构 / 钩子 / 标题公式 / 支招框 / 排版）。
- **图片贴图（`图片贴图`）**：内容大部分在图片里（公众号贴片 / 卡片图），HTML 正文几乎为空；
  必须先 OCR（§2）取出图中文字。其 writing_craft 描述「图片卡片序列」结构（封面 + 引言 +
  N 张图文卡片 + 结尾卡），生成时产出是**配图 / 卡片规格**（自然语言卡片文案：每卡 = 标题 + 一段正文 + 一个 tip 框），
  **不是字段标注文档**——提取与生成都不得输出 `## 【卡片N】`、`- **场景代入**：` 这类结构标签，字段仅作内部思路。
  封面主/副标题约束（各 ≤15 字、副标题前固定 `✅`、由 `xhs-title-factory` 拟定，禁止手写）见 `writing_rules_anti_pattern.md` 硬规则8；占位符注解（如 `（{baby_name}）`）与给校对员的元指令
  （如「人工核对提示」）**不写进最终文件**，仅在对话中口头说明。

**存储**：writing_craft 与 frequency_notes 按内容类型分存于 `profile.content_modes`：

```json
{
  "content_modes": {
    "图文文章": {
      "extraction": "text",
      "writing_craft": { "<见「行文工艺字段」>" },
      "frequency_notes": { "<见 §6>" }
    },
    "图片贴图": {
      "extraction": "ocr_required",
      "ocr_status": "pending | done",
      "source_files": ["贴图源文件 1", "..."],
      "writing_craft": { "<图片卡片序列骨架，OCR 后补全；须含 title_style（封面主/副标题各≤15字且各自独立计数；副标题前固定✅；主副标题由 xhs-title-factory 拟定）>" },
      "frequency_notes": { "<见 §6，须用实测计数>" }
    }
  }
}
```

> 兼容：人设也可保留顶层 `profile.writing_craft` 作为「图文文章」默认模式；`content_modes`
> 承载额外的非默认模式（如 图片贴图）。生成时按内容类型选对应 writing_craft。

### 提取要点（content_modes）

- 拿到素材先按 §1 **逐篇判定内容类型**，再分堆分别提取各自 writing_craft + frequency_notes。
- 贴图模式在 OCR 完成前只记结构骨架（封面 + 引言 + N 卡片 + 结尾卡）并标 `ocr_status: pending`；
  **不得把「无正文」误判为「作者不写案例」**；OCR 后补全卡片标题公式 / 支招框视觉 / 单卡字数画像（写入 `writing_craft.length_profile.per_item_chars`）/ frequency_notes。
- 两种模式的 voice / 支招框名称统一到人设品牌（§7），不因来源作者而异。

```json
  "writing_craft": {
    "structure": ["痛点引入","问题拆解","3-5 点清单支招","个人案例(可选)","总结金句","互动引导"],
```

**映射规则**（扁平清单 → 嵌套 profile）：

  `keywords` → `style.vocabulary`；`rhetoric` → `style.rhetoric`；`values` → `values`；`taboos` → `avoid`

## 命名建议

名字应可识别且区分度强，推荐格式：
- `角色·风格`，如 `科技评论员·犀利理性`

- 如用户已给名字，直接采用。

## 落库命令

与人设一同提取时，放入 `add` 的 profile 内：

```bash
python <skill_dir>/scripts/persona_manager.py add --data '{
  "name": "育儿博主·温柔陪伴",
  "source_articles": ["..."],
  "profile": { "<identity/style/...>", "content_modes": { "图文文章": { "writing_craft": {...}, "frequency_notes": {...} } } }
}'
```

已有人设补提 / 修订时，用 update 合并（深层字段自动 merge，不覆盖 profile 其它部分）：

```bash
python <skill_dir>/scripts/persona_manager.py update "<id 或名称>" --patch '{
  "profile": { "content_modes": { "图片贴图": { "ocr_status": "done", "writing_craft": {...}, "frequency_notes": {...} } } }
}'
```

补丁较大时写成 JSON 文件用 `--file` 传入。**禁止手工拼接 personas.json**。
