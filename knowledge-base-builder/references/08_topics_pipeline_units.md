## 1. 层1 内容主题层

六维标签（domains/forms/tools/types/projects/sources）是**属性**，决定"在哪个模块/项目被拉到"；
**内容主题 topics** 是生长式标签，决定"这篇讲了哪几件事、跨文档怎么聚合"。两者并存。

- 每篇 1–5 个 topics（自由生长、非受控）；规则打标不猜主题，由 AI 读高价值块标注。
- `q_hooks`（每篇 3–5 条口语问法）与 topics 同属内容层：topics 回答"这篇讲了哪几件事"，`q_hooks` 回答"用户会怎么问这件事"。录入（深抽）时顺手生成，检索时优先匹配，见 `06_retrieval.md` 第 8 节。
- `build_topics.py` 聚合 `_meta/topics.json`（topic → docs / summary / open_questions）并渲染 `00_导航/主题地图.md`；`--notes` 默认 **`工作流`**（与 `search_index.py` 一致），笔记目录不存在或 0 篇时非 0 退出、不写空产物。
- 同名/近义主题由 AI 给归并候选、人工确认，**不自动合并**。

## 2. 层2 两阶段与切块参数

不要对几千篇逐块全量深抽。先出文档地图，只深抽高价值块。

### 切块（doc_map.py）

- 按 markdown 标题（#/##/###）或妙记时间戳切块；
- 块长参考 **800–1500 中文字**，overlap 约 10%（跨标题边界时保留衔接句）；
- 无标题的长文按 1200 字软切。

### 高价值块判定（启发式，只粗筛；技术与非技术文档都要覆盖）

- 长度 ≥50 且（密度分 ≥0.5 或含代码块）→ 高价值；
- **技术特征**：代码块 +0.6、≥3 个数字 +0.3、行内命令 +0.3、外链 +0.1；
- **非技术特征**（课程/理论/SOP/分析，避免误判为低密度）：
  - 标题含"定义/概念/原理/方法/步骤/流程/注意/结论" → +0.3；
  - 正文含"因为/所以/导致/意味着/关键在于" → +0.2；
  - 连续叙述段 ≥80 字且有完整主谓 → +0.2；
- 低密度块记 `skip_reason`，不硬抽；**但低价值块按 5% 抽样人工复核**，发现漏判只对新批次调 doc_map 规则，不回滚已处理批次。

### 两阶段

- **阶段 A**：`doc_map.py` 输出 `_meta/doc_maps.jsonl`（每篇 chunks + coverage）；
- **阶段 B**：AI 只读高价值块，深抽为笔记 / units；**进度不回填 `doc_maps` 的 `coverage`**
  （`chunks_processed` / `high_value_done` 是生成时快照、**已作废**，见 `04_pipeline.md` §12.2），
  跑 `progress.py` 从笔记反推；低价值块不抽。
  深抽时逐篇遵守第 3 节硬约束、第 3.5 节 q_hooks 规约与第 3.6 节双链规约；
  第 3.6 节要求的**可引名单在每批深抽开始前刷新一次**，作为写正文时的输入上下文。

## 3. 深抽硬约束（不幻觉，执行 AI 必须逐条遵守）

1. **只依据给定原文**：不补任何外部知识、常识、"通常应该如此"。
2. **无来源写 null**：找不到原文对应处时，evidence 写 null，**禁止编造**章节/字符/引文。
3. **数字/日期/命令/代码逐字保留**：不改写、不约数、不翻译；任何改动都要在 inference 里说明。
4. **事实与推断分离**：原文支持的进 type/evidence；AI 的理解单列 `inference`，不混入正文。
5. **不确定标 low**：confidence=low 且进收件箱，不硬判为 high。
6. **冲突不合并**：两篇说法不一致 → 建 conflict 单元，保留双方来源，不擅自取舍。
7. **不省略关键步骤**：procedure 的步骤顺序、前置条件、异常分支必须保留，不得"概括成一句"。
8. **引用必须给 locator**：任何 claim/数值/命令都带 `§章节#字符范围`，可回原文核对。
   **locator 由脚本算，模型/人只交 quote**：`scripts/autolocate.py --compute --src <源文件> --quote "<原文逐字>"`
   打印 `§标题#char=a-b`，标题取自 `_meta/doc_maps.jsonl` 里包住该 char 的块 heading，**不手抄**（手抄标题
   正是上一批"区间对、标题错"那类错位的来源）。四种形状各有归宿：唯一命中 → 给区间；
   多处命中 → 报歧义并打每处 ±30 字上下文（rc=2，要求加宽上下文）；零命中 → rc≠0 且**拒绝编造区间**
   （中间会去空白/去标记再试一轮，那轮命中时在 `how` 里明写"引文与原文不是逐字相等"）。
   笔记落盘后用 `--check <笔记.md>` 复核：它是**门禁不是提示器**——evidence 区间复算不等、
   或清单行 `[char=a-b]` 指向的不是该行文字在本篇已立据区间里最贴合的那一个，都 rc≠0。
   **一行多据时拆行，不扩文法**：`[char=a-b]` 保持单数形状是刻意的——拆行会把"这一行到底靠哪条原话"逼出来，
   扩成一行挂多个区间则等于把跨据综合藏进清单行（跨据的综合归「归纳结论」段，那里不受本门禁管）。
   与 warn-only 的 `check_verbatim_lite.py` 分工：那边管"内容有没有漏抽/多写"，这边管"区间与标题是不是真"。
   **来源是转换产物时**：`scripts/convert_sources.py` 把 `.docx/.epub/.odt` 转成的 md 落在
   `<kb>/_meta/converted/` 下，**转换产物的路径以 `_meta/converted/` 为根**，`sources` 与 quote/char
   一律对**产物**计算；产物是**派生物**，与 `doc_maps.jsonl` / `search.db` 同级，可删可重建。
9. **按语义单元拆，不按块拆**：块是**输入容器**，不是笔记粒度定义。一个高价值块里装着 6 件可独立回答的事，
   就出 6 篇笔记；一篇笔记只回答一个问题。**不许把多件事塞进一篇，也不许因为"这块已经抽过一篇"就不再抽**。
   反面判据（三条都算拆篇失败，不是缺陷清单而是抽检项）：① 标题里有"和/与/及"串起两个不相干结论；
   ② 归纳层出现两个互不依赖的判据组；③ 一句话摘要需要"并且/同时"才能说完。
   一个语义单元跨块时：主块进 `source_locator` 首项，其余块按引用顺序列在后面（见 `04` §2.3），
   **不要把非路径内容写进 `sources`**——C5 要求每一项都是真实文件路径，写进去即 FAIL。
   **候选边界哪来**：`scripts/split_boundaries.py`（只读源料、只写 `--out`）。它**不是第二套切块口径**——
   `doc_map.py` 按标题切块这条约定一字未改，它只在块**内部**列候选边界，定篇仍由深抽按语义判。
   四类标记的处置（本批定稿，括号内为 05 全目录实测）：
    - `media_table`（**按内容判**：URL／文件名／`![缺失素材:None]` 一类单元格过半）＝素材索引表，
      **彻底不产笔记**，只在来源笔记里登记一句「本块另有 N 项素材表」。**例外**：「文字·数据·标准」型
      表格是论证本体，按语义正常参与拆篇（反例基准：`#60` 的「手动版 VS 进阶自动化」对比表必须留）。
      实测 185 单位 / 85,807 字（发现 37 修复后；修前漏判 1 单位／116 字，因为它被吞进了错配的围栏）
      ——**用候选段数估工时必须先扣掉它**（`#12` 单块否则高估 3.5 倍）。
    - 代码围栏＝**整体不可切**，且与它的说明段落粘连；粘不下才独立成段，独立且超 LIMIT 者标
      `oversized_fence`。闭栏必须是**整行纯反引号、且反引号数 ≥ 开栏数**——05 里有 5 处用四个反引号开栏
      的模板（里面嵌 ``` 示例），只认"恰好三个反引号"会把闭栏认漏，实测 5/5 配错、最多的一处把围栏外
      11,333 字正文连素材表一起吞成"不可切的原子段"（发现 37）。
    - **`oversized_fence` 分两档**（本批裁 ②）：
      · **≤ 3,000 字**（＝2×LIMIT）→ **算一篇**资产笔记，宁可一段超长也不劈代码／劈提示词模板；
      · **> 3,000 字** → **不产原子笔记**，改在**来源笔记**里做**资产登记**：整段 locator ＋ 一句
        「名称／版本／用途」，并汇进该 flow 的 `_提示词资产.md` 聚合页（`_` 前缀＝聚合页，
        不进 C4/C12/A1–A6 的篇数口径）。
        为什么：这类块是**整份 agent 配置（JSON）或长样例/长 SOP**，不是可摘引的资料原话，塞进原子笔记
        必然撑破"一篇只回答一个问题"（05 实测 >3,000 字共 9 段：2 段整份配置＋其 2 份跨文档副本＋
        4 段长样例＋1 段长 SOP，最长 17,506 字）。要不要另拆"这份配置的设计要点"笔记，由**人工**定，
        不由脚本定。
      05 实测（发现 37 修复后）：`oversized_fence` 29 段＝≤3,000 字 **20 段** ＋ >3,000 字 **9 段**。
    - **同一份资产重复出现**（实测两类各一例：跨篇「分镜师 v3.2」17,506／17,501 字，只差围栏语言标签；
      同篇两处 1,585 字逐字相同）→ **只建一篇 ＋ 多个 locator**，不出第二篇。
      去重键用**归一化内容**（抹空白与反引号后比），不是原文 sha——副本常只差一个 ```Plaintext／```JSON 标签。
    - 超 LIMIT 的普通单位＝**先与前段粘连**（前段是引子：以标题行/冒号/破折号结尾，或 ≤400 字），
      **禁链式**；粘完仍超标 `oversized_frag`——它就是本条「按语义再拆」的对象。
      **绝不允许在无结构处硬切造边界**（v1 按 1,500 字硬切，实测把签名 URL 与表格劈成半行碎片）。
      实测 11 段，段首 11/11 是引子形状（`## 附：ASR 术语矫正对照表` 一类）。
    - `dense`＝候选段内 ≥2 个伪标题 ⇒ 本条要求**必拆**，不是"可以考虑拆"。实测 1,151 段。
   **深抽的提交单位 = 一篇文档一批**：把该篇全部候选段（含 `dense`／`oversized_fence`／`media_table` 标记）
   一次性给模型，**一次返回 N 篇**；**不要一块一往返**。
   成本口径两句写死：① 省的是**会话往返次数**与**每轮重复注入的上下文**（名单、规则、同一篇的其余段落
   不必再重讲一遍）；② **不是 API 折价**——本库**没有模型客户端**，深抽的执行者就是会话里的 AI，
   计价口径不由这条流水线控制，谁也别在文档里承诺"打折"。

10. **禁用签名 URL / 导出占位作 evidence**：正文里的预签名链接（`x-oss-expires=`、`x-oss-signature=`
    一类）与 `![缺失素材:None]`、「未随文复刻，请回原文查看」这类占位，**都不是可回放的证据**——
    签名 24 小时后必然失效、占位的素材从未导出过。要留就写成**事实句**（「此处原为飞书画板，未随文导出」），
    不得把这类链接当 `evidence.quote`，也不得据它补写内容。
    为什么只能靠写的人守：C5 只校 `sources` 的**文件路径**、C14 只比源目录 sha256，
    **正文里的死链没有任何校验会报**（登记为发现 36）。机器侧的兜底是
    `scripts/check_verbatim_lite.py` 的「失效资产」warn（warn only、不判失败）。

> 违反任意一条的单元，validate 应判错并退回本批。
>
> **units 关闭时谁来守第 3 条（数字/命令逐字）**：`validate_extraction.py` 的逐字校验只在 units
> 路径上跑（且只覆盖 `type=="claim"` 的 `text`/`metric`），所以 **units 关闭时，正文数值/命令逐字校验
> 由 `scripts/check_verbatim_lite.py` 承担，替代 validate 的数值逐字检查**。它是 **warn only、exit 0**
> 的提示器不是门禁：「多」（笔记有、本篇引用的块里没有）是主判据，「缺」（主块有、笔记没有）是参考信号
> ＝1:N 的拆篇候选。它检不了的东西在输出 `not_checked` 里逐条明写，别当成全检。

### 3.1 标注规约：inference 段的四种前缀白名单（写死，units 关闭时的逐字校验依赖它）

`## AI 推断（inference）` 段里**每一行必须以且只用这 4 种前缀之一开头**：

| 前缀 | 装什么 | 逐字校验 |
|---|---|---|
| `作者未提、我的推论：` | 模型自创的判断、建议、阈值 | **豁免** |
| `同块其他结论：` | 同一块里没独立成篇的其余结论（转述原文） | 照正文校验 |
| `口径澄清：` | 对原文数字/说法适用范围的提醒（"这是作者口径不是数据"） | 照正文校验 |
| `⚠️` | 资料残缺、不可复核、外链未核验等警示 | 照正文校验 |

> **护栏句（是规约不是建议）**：inference 段每行必须以这 4 种前缀之一开头；**无前缀的 inference 行视为违规，抽检项**。
> 白名单进规约要挡两件事：① 免责只给"**声明过的**自创"，混在归纳里的改写照样追责；
> ② 抽检能看见谁在用哪一类前缀——**前缀不是逃生门**。

为什么不做"整段豁免"：真库实测里，`4 张产出物缩图`（源里那块实际是 7 处图片引用）和
`5 段式拆解模板`（源里实际是 6 段链）这两次真实失手，**都写在 inference 段内**。整段豁免 =
承认"把失手挪进推断段就免检"合法。按前缀分治才分得开"自创"与"转述/警示"。

`scripts/check_verbatim_lite.py` 的豁免规则就是这张表：**只豁免 `作者未提、我的推论：` 开头的行**。

> **配套的两条写法约束（都是真库实测撞出来的，不是洁癖）**：
> ① **谈本库结构/渲染/字段的元语言里不要写裸数字**——「改成 1/2/3」「`1.` 这样」里的数不属于原文，
>    会被「多」方向报成自创。要谈就用中文数词（一二三）或挪进 `作者未提、我的推论：`。
> ② **本库自数的语料元数据（图片引用数、块数、字数）写进来源笔记，不写进原子笔记正文**——
>    那些数原文里没有，进正文就必然报「多」；来源笔记本来就是把语料事实说清楚的地方。

## 3.5 q_hooks 生成规约（深抽时执行，AI 遵守）

`q_hooks` 是**同义召回的口语入口**——存的是「用户会怎么开口问」，不是「这篇讲了哪些词」。
关键词归 `topics` 与六维标签；把它当关键词别名表填，等于往索引里灌一批和正文同分布的词，
起不到同义召回的作用。

**触发**：笔记入库时，若 frontmatter 无 `q_hooks` 或为空数组 → 生成 **3–5 条**。
已有 `q_hooks`（人工或模型写的）→ **默认不覆盖**（增量路径没有开关，是否覆盖由执行 AI 按本规约判定；
存量路径的唯一实体开关是 `backfill_hooks.py --force`，见 `06` 第 8.3 节）。

**输入给模型的上下文**：标题 + `topics` + 正文。三者定稿后才生成，生成完再落盘。

**输出**：JSON 数组，3–5 条，每条是一个**真实用户可能问出口的话**。

**质量红线（成败关键，逐条遵守）**：

1. **禁止标题复述**。把标题加个「怎么 / 为什么」不算 hook；
2. **禁止关键词堆砌**。「爆款 视频 分析」不是问法，是查询串；
3. **禁止与正文原句雷同**。hook 是「别人会怎么问」，不是「文章怎么写的」；
4. **每条须含至少一个本篇特有的实词**，不得只靠泛化 bigram（分析 / 视频 / 内容这类）命中；
5. **至少覆盖 3 个不同角度**：what（是什么）/ how（怎么做）/ why（为什么）/
   compare（和什么对比）/ scenario（什么场景用）/ boundary（什么时候不适用）。

> **第 6 条不是语义红线，是格式取舍（发现 15 登记）**：**hook 条目内禁用逗号**（`,` 与 `，`）——
> 因为非数组写法会被按逗号**静默 split** 成两条，一条带逗号的 hook 在内联写法下会碎成两截。
> 这是**为 YAML 兼容性做的取舍，不是真理**：**登记为可放宽项**。
> 下一轮可考虑「**强制 block 语法 + 允许条目内逗号**」，那样逗号就不再是分隔符；
> **本轮按现规则跑**（`check_hooks.py` 的原因码 `comma_in_item` 照报，规则见 `06` 第 8.2 节）。

**校验**：落盘后跑

```
python scripts/check_hooks.py --notes-dir 工作流 --warn-log _meta/logs/q_hooks_warnings.jsonl
```

必须在 `search_index.py build` **之前**跑。schema、原因码、降级与覆盖细则见
`06_retrieval.md` 第 8.2 / 8.3 节。**角度覆盖不做机械判定**（角度标记不进 frontmatter，
否则要改 schema、动检索侧），靠本规约约束 + 人工抽检兜底。

**降级**：生成失败 / 输出非 JSON / 校验不过 → **不阻塞入库**，`q_hooks` 置空 `[]` + 记一条
warning；置空动作由**执行 AI** 做——`check_hooks.py` 对笔记零写入权。

**存量回填**：老笔记补齐 q_hooks 走 `scripts/backfill_hooks.py`——生成者仍是本节的执行 AI
（脚本不生成内容），脚本只做扫描 / 校验 / 落盘，且**只补缺、默认不覆盖**。见
`06_retrieval.md` 第 8.3 节。

## 3.6 笔记间引用双链规约 + 可引名单（深抽时执行，AI 遵守）

### 3.6.1 规约原文

> 笔记间引用双链：写正文时，只有当正文明确引用、依赖或对照库内某篇已有笔记的
> 具体内容/结论，并且读者需要跳转到该笔记才能完整理解时，才在该处写
> `[[目标笔记]]`。加链前确认目标笔记存在且可解析。不得因同 topic、同标签、
> 同概念或泛泛相关而加链；不得为每篇笔记主动寻找关联；无明确引用则不添加，
> 允许笔记保持孤岛。双链只表示引用跳转，不承载概念关系；概念关系仍由
> `relation` 单元表达。

**这条是建模规约，不是脚本能力**：不加 `--link` 参数、不写自动补链脚本、不做边密度或
连通性校验。链由执行 AI 在写正文时按上面这段话决定，脚本只负责事后校验目标是否存在。

### 3.6.2 目标笔记名的口径（写错一处，两套校验器一起响）

`[[目标笔记]]` 里填**文件名去掉 `.md` 的部分（stem）**，不填标题、不填相对路径。

| 校验处 | 解析口径 | 后果 |
|---|---|---|
| `verify.py` C10 | 只认 `工作流/` 下笔记的 **stem**（`note_stems`） | 写成标题 → 判失效链接（warn） |
| `audit.py` A1 explicit | 路径 / 文件名 / **标题** 三种都认（复用 `search_index._unit_doc_path`） | 同一条链 audit 认、C10 不认 |

audit 比 verify 宽，所以**只按标题写链会出现「audit 有边、C10 报失效」的分裂结果**。
统一以 stem 为准即可两边一致。可引名单里同时给出 stem 和标题，**加链时取 stem 那一列**。

> C10 先把全库 stem 收齐、再判每条链的目标存在性，所以**引用同批里排序靠后的笔记不会被误判失效**
> （深抽是按块写的，被引用的一篇完全可能比引用它的那篇晚落盘）。
> 失效链接只出 **warn**、不 fail，也不影响 exit——链的目标存在性是校验，加多少链不是。

### 3.6.3 可引名单：深抽前注入的上下文

深抽某篇笔记前，先扫描 KB 现有笔记，把名单作为上下文注入深抽提示词，模型写正文时手边可见。
**注入的节奏跟"一篇文档一批"走**（§3 第 9 条）：一批开始前扫**一次**就够了，不必每个候选段各扫一次——
同批内后写的笔记引用先写的笔记，由 C10"先收齐全库 stem 再判存在性"兜住（见 3.6.2 末），不会因为排序靠后被误判失效。

| 字段 | 来源 | 备注 |
|---|---|---|
| `doc_id` | 笔记相对 KB 根的路径，如 `工作流/视频制作/1_找素材/选品四象限.md` | 与 `audit.scan_notes`、`build_topics.collect` 同口径 |
| **stem（加链用这个）** | 文件名去 `.md` | 见 3.6.2 |
| 标题 | frontmatter `title:` | 仅用于认读，**不作链的目标** |
| topics | frontmatter `topics:` | 名单里出现同 topic **不构成**加链理由 |
| 一句话摘要 | frontmatter `summary:` → 没有则取正文首个 `> ` 引用行（模板里的「一句话结论」）→ 再没有则取正文前 60 字 | 三级回退，取到哪级算哪级 |

生成方式：**执行 AI 用只读手段扫一遍笔记目录**（一次遍历取 frontmatter + 首段即可），
不产出新脚本、不写任何文件。名单每批刷新一次（批量入库见 `SKILL.md` Step 7），不必每篇一刷。

**名单是「可引名单」，不是「必引名单」**。名单头部固定带一句：

> 下列为本库现有笔记，仅供正文**确实引用**时跳转使用。出现在名单中、同 topic、同标签、
> 同环节都**不是**加链理由；正文没有明确引用就一条链也不加。

### 3.6.4 规模控制

- 阈值：**默认 200 篇**（可配，写在 KB 的 `config.json` / `AGENTS.md` 口径里，不是 CLI 参数）。
- **≤ 阈值**：全量注入，按 `flow / stage` 分组、组内 stem 字典序。
- **> 阈值**：按相关性分层填，**总条数封顶 200**，每条一行 `stem ｜ 标题 ｜ topics ｜ 摘要`，
  并标注来自哪一层：

  1. **T1 同来源文档 ∪ 同 `<flow>/<stage>` 目录**——一篇原文拆成多块时最容易互相引用，优先给全；
  2. **T2 topics 有交集**：与本批高价值块预标 topics 有交集的笔记，按**交集个数降序**、再按 stem 字典序；
  3. **T3 补足**：`_meta/topics.json`（`build_topics.py` 产物，含 topic→docs 与 doc_count）里
     doc_count 最高的主题下笔记，只让模型知道"库里还有这些主题"。

  同一篇笔记只按最先命中的层出现一次，不重复列。

- token 量级：200 条 × 约 40 字 ≈ 8k 字，一批一次，可控。
- ⚠️ **T2 自带偏见**：用 topic 筛就是把同 topic 的笔记推到模型眼前，而规约禁止因同 topic 加链。
  双保险 = 规约原文照抄 + 名单头部那句提示 + 每条标来源层；名单只回答"库里有没有这么一篇"，
  不回答"该不该链它"。

### 3.6.5 边界：本规约只管原子笔记正文

`_流程.md`、`_总览.md`（`build_flows.py` 产物）与 `00_导航/主题地图.md`（`build_topics.py` 产物）
里的 `[[笔记]]` 是**导航列举**，不是正文引用，也不做加链判断——它们由脚本从聚合关系生成，
verify C10 本就跳过 `_` 前缀聚合页、且**内容只扫 `工作流/`**。**不要因为"聚合页里全是链"就认为
笔记之间该有链。**

> **但 C10 的"目标在哪儿找"比"内容扫谁"宽**（发现 28）：上面模板要求留的 `来源：[[来源笔记链接]]`
> 是真引用，而来源笔记物理上住在 `素材库/_来源地图/`。C10 因此把**目标解析全集**扩到
> `工作流/` + `素材库/_来源地图/`（`verify.py` 的 `SCAN_DIRS` 与 `STEM_SOURCE_DIRS` 两个常量分家）。
> 两个残留要说清，别当成已全修：① 判据没变，仍只判"目标存在"；② **来源笔记自己正文里的出链**
> 依然不在被检范围（内容仍只扫 `工作流/`）。**这条是"未定"不是"未修"**：来源笔记的正文是人写的、
> 非原子笔记结构，它**该不该受 C9（三段分标）/C11（主轴位置）管**本身是个没答的设计问题——
> 扩 `SCAN_DIRS` 会顺带把这两道检查压到来源笔记上，而它没有 flow/stage、也没有三段。
> 先定性质，再谈改法；别下一轮当 bug 直接动手。

**模板侧同步（防止模板把规约带回去）**：`assets/templates/note_atomic.template.md` 的「关联」节
**不再预留 `[[相关笔记]]` 占位**，只留 `来源：[[来源笔记链接]]`（来源指向是真引用）；
`note_card` / `note_deep` 的关联节改为"无引用则删掉本节"；`note_topic` 的同类节改名为
「本主题成员笔记（聚合列举，不是正文引用）」。模板里出现一个空 `[[]]` 位置，等于让每篇笔记
进场时就欠一条链——这正是本节要消除的行为。

**来源链的性质（发现 27 定稿）**：模板留的 `来源：[[来源笔记链接]]` 是**可选**的，不是必填。
- **缺了不算缺陷**：C10 不判它、`verify` 任何一项都不判它、`check_hooks` 与逐字校验也不看它——
  **不进任何机器校验**；
- 它是**抽检项**：人工抽检时看"本批有没有按模板给来源指一条路"，缺就记一条抽检事实，不返工；
- 口径与显式双链完全一致，**不另立标准**：`10_audit.md` 的 A1 已经写死「**A1 explicit 是诊断指标，
  不是通过条件**；边数 0 与边数 100 在 audit 眼里只是两个分布」。链（含来源链）是**可选的语义副产品**，
  写它的唯一理由仍是第 3.6.1 节那句「读者需要跳转才完整理解」。
- 反面教训（实测）：真库 8 篇新笔记**一条来源链都没写**，同时 0 缺陷、verify 全绿——
  说明"没写"本来就不该被当成问题；**别为了绿屏去补链**，也别把来源链塞进机器校验。

## 4. 层3 units：分类型 schema

通用字段（所有类型）：

> **三段语义写死**（对应硬规则"资料原话/归纳结论/AI 推断"）：
> - `evidence.quote` = **资料原话**，必须逐字、validate 校验它是原文子串；
> - 各类型主字段（text/name+definition/goal+steps…）= **归纳结论**，允许改写、压缩、结构化；
> - `inference` = **AI 推断**，不进主字段、不进 evidence，单独标注。
> 三者不可混：归纳不得当原话校验，推断不得当结论放行。

```json
{
  "id": "doc-x-claim-1",
  "doc_id": "doc-x", "chunk_id": "doc-x-2",
  "topic_ids": ["Codex剪口播"],
  "type": "claim",
  "confidence": "high|medium|low",
  "status": "draft|confirmed",
  "inference": "可选，AI 理解，与原文分离",
  "evidence": {"file": "raw/a.md", "locator": "§3#char=1200-1280", "quote": "原文短引"}
}
```

> `evidence` 可为单对象；**合并/跨块后转为对象数组**（每段一个 file+locator+quote），不得只留一条。

单元类型共七类：**claim / concept / relation / procedure / qa / open_question / conflict**。
开 units 后默认只抽**核心四类**，扩展三类按目标推断或用户显式要求开启（口径与 `build_units.py` 的 `CORE_TYPES`/`EXTENDED_TYPES`、`config.extract_units` 三方一致）：

- **核心四类（默认开）**：claim / concept / qa / open_question；
- **扩展三类（用户要"关系/SOP/冲突"，或 Q4 痛点含 c"不知下一步学啥"、或 Q13.1 输出含 d"以后做 RAG"时开）**：relation / procedure / conflict；
- asset（模板/清单）始终为可选。

### claim · 知识点（即用户语境中的"知识点"）
覆盖事实、规则、方法、结论、指标。`case`（案例）、`metric`（指标）为可选字段，
避免案例和数据被硬塞进 text。
```json
{"type":"claim","text":"先跑5篇样板再批量",
 "conditions":"新库首次入库时","scope":"个人批量入库",
 "case":"Codex剪辑库首批评测","metric":"样板F1=0.88",
 "evidence":{...}}
```

### concept · 概念
```json
{"type":"concept","name":"第二大脑",
 "definition":"把外部信息沉淀为可检索笔记的系统",
 "aliases":["PKM","第二大脑"],"boundary":"指个人知识管理，非团队 wiki",
 "evidence":{...}}
```

### relation · 概念关系（跨文档概念网络）
```json
{"type":"relation",
 "subject":"第二大脑","predicate":"包含","object":"提炼笔记",
 "relation_type":"组成|因果|依赖|对比|时序|上下位",
 "evidence":{...}}
```
> `relation_type` 首选受控六值；长尾新值先标注、人工确认后写入 `taxonomy.json`，不直接生效。

### procedure · SOP/流程（步骤顺序必须保留）
`steps[]` 每项可带可选 `locator`（该步来源）；跨 chunk 拼接时顶层 `evidence` 保留首尾段。
```json
{"type":"procedure","goal":"用 Codex 自动剪口播",
 "preconditions":["已装 Codex","有口播素材"],
 "roles":["剪辑","Codex"],
 "steps":[{"order":1,"action":"导入脚本","locator":"§2#char=100-200"},
          {"order":2,"action":"匹配素材","locator":"§4#char=50-120"}],
 "exceptions":"无配音时跳过 BGM 步",
 "acceptance":"成片导出无跳帧","evidence":{...}}
```

### qa · 问答
```json
{"type":"qa","question":"要不要一上来就上向量库？",
 "answer":"不要，先 FTS5 用顺","answer_type":"建议","evidence":{...}}
```

### open_question · 待验证/矛盾
```json
{"type":"open_question","question":"该工具是否适合团队？",
 "reason":"资料只讲个人用法","impact":"影响是否推广","evidence":{...}}
```

### conflict · 多来源冲突（不合并）
`positions[]` 每项带 `locator`，双方出处都可回原文。
```json
{"type":"conflict",
 "sources":["raw/a.md","raw/b.md"],
 "positions":[{"source":"raw/a.md","text":"参数用 --fast","locator":"§1#char=10-30"},
              {"source":"raw/b.md","text":"参数用 --turbo","locator":"§2#char=40-60"}],
 "arbitration_note":"仅标注时间/权威/适用范围，不自动裁决",
 "time":"a=2025-12 / b=2026-03","evidence":[{...},{...}]}
```

> asset（模板/清单/可复用片段）为可选类型，用户明确要时再开。

## 5. 冲突处理

- 同一主题/命令/SOP 出现矛盾 → 建 `conflict` 单元，**保留全部来源**；
- 仲裁只标注（时间新旧 / 来源权威 / 适用范围），**不删除任何一方**；
- conflict 单元在主题索引里高亮，等人工拍板；
- 禁止把两种说法平均成一条"折中结论"。

### 5.1 单元归一与合并（不丢信息、不冗余）

- **同 doc 同名 concept / relation**：合并为一条，`evidence` 保留多个 locator（数组），不删原文出处；
- **跨 doc 同一 claim**：**不自动合并**——用 topics 聚合，检索时并列展示两篇，避免混淆来源；
- **跨 chunk 的 procedure**：按 `steps.order` 拼接成一条，evidence 保留多段 locator；若顺序冲突，转 conflict；
- **任何合并都必须保留全部 evidence**，禁止只留第一条 locator；合并后**保留首次出现的 id**，其余旧 id 不物理删除。
  > ⚠️ **当前 units 不记 alias**：`build_units.py` 不写 alias 表，旧 id 无法反查，
  > 所以"合并前声明条数"**不可校验**。第 8 节第 7 项只能检三种可检的削痕形态
  > （三要素不齐 / 重复 locator / 跨段只留一条）。**不要把这三种当成合并全检**，
  > 也不要顺手给 units 加 alias 字段——那要动 `build_units.py` 的数据结构，超出结构校验范围。

## 6. 块级 locator

格式：`§章节标题#char=起始-结束`（doc_map 已给出每个 chunk 的字符范围）。

- claim/procedure/数值/命令/代码必须带 locator；
- validate 会按字符范围回原文核对 quote 是否真在该段。

## 7. 覆盖审计 coverage_audit.jsonl

每 chunk 一行（深抽后由执行 AI / 脚本回填）：

```json
{"doc_id":"doc-x","chunk_id":"doc-x-2",
 "locator":"§3#char=1200-2000",
 "status":"extracted|skipped|inbox|failed",
 "units":["doc-x-claim-1","doc-x-procedure-1"],
 "skip_reason":""}
```

- **extracted**：已深抽并产出 units；**skipped**：低价值（记原因）；
- **inbox**：低置信/冲突待人工；**failed**：处理失败，必须进问题资产库。
- skipped 可后续补抽；failed 不允许静默丢弃。
- 门禁：所有 `high_value=true` 的 chunk 必须为 extracted 或 inbox（不能漏抽）。
- **inbox 占比门禁**：本批 inbox 的 high_value chunk 占比 >20% → 视为没抽出来，本批不放行，先改深抽提示词再重跑（不能用"全进收件箱"蒙混）；**小批次（high_value chunk <10）不按比例，改人工判断是否放行**，避免 1/3 就误拦。

> **这份账的定位（与进度派生器的分工）**：`coverage_audit.jsonl` 记录**块级跳过原因**；
> 进度事实以 `progress.py` 反推为准。**两者冲突时 progress 赢，`coverage_audit` 标过期**——
> 不要把它的"已抽"字段当权威源。它唯一的机器消费者是 `validate_extraction.py --coverage`
> （默认 `_meta/coverage_audit.jsonl`，判上面第 6 条"高价值块未抽"），**只覆盖 units 开启路径**；
> units 关闭时这份账**没有任何脚本校验**，靠人工核对。schema 不因本条口径改动。

## 8. 引用与数值校验（validate_extraction.py）

确定性批量校验，不靠人工：

1. **quote 回原文（严格子串）**：按 evidence.locator 取原文片段，quote（仅去空白）必须是原文子串，**不允许任何改写/纠错/归一**；原文错别字也照抄，想纠正写进 inference；
2. **数值/命令/代码逐字、不归一**：`1,000` 与 `1000`、`50%` 与"百分之五十"算**不通过**；要归一化在 inference 说明，不在正文改；
3. **high 必有证据**：confidence=high 的单元，evidence 三要素必须齐全；
4. **procedure 步骤连续**：steps.order 必须从 1 连续无缺；
5. **conflict 双源**：positions 至少 2 个来源；
6. **高价值块未抽**：doc_maps 里 high_value=true 的 chunk，coverage_audit 必须有 extracted/inbox
   （**仅 units 开启路径可检**；units 关闭时无人检这条，进度看 `progress.py`）；
7. **合并留痕（§5.1「禁止只留第一条 locator」）**：只检**三种可检形态**——
   ① `evidence` 数组里某项三要素不齐；② 合并的多条指向**同一个** locator（假合并）；
   ③ `procedure` 的 `steps[].locator` 跨 ≥2 段、顶层 `evidence` 却只留 ≤1 段。

**输入守卫**：`units.jsonl` 不存在或 0 条 → **exit 1 并拒绝打印「通过」**。
units 是可选辅助层（第 11 节）——**没开 units 的库不要跑 validate，它不是非 units 路径的放行依据**。
以前没有这条守卫：空输入 → 六项检查全 0 → 「通过 ✓」exit 0，把"整批没抽任何东西"报成"抽得没问题"。
退出码现在才真成立：`main()` 的返回值已接到进程退出码上，任何一项不过即 exit 1。

**能力边界（别当成全检）**：units **不记 alias**，所以"合并前声明了几段 evidence"不可反查。
第 7 项只能抓住上列三种残留形态；`validate_report.json` 用
`merge_count_checkable: false` + `merge_note` 明写这一点，不假装合并被全检过。

输出 `_meta/validate_report.json`：各类错误计数与明细；有错则本批不放行（exit 1）。

## 9. 抽检与不通过处置

- 每批人工抽 **5–10 条**，覆盖不同文档类型/单元类型（claim/procedure/relation/qa 都要抽到）；
- **统计单位 = 抽检条目**（不是整批文档）：条目级通过率 <95% → 本批回滚到 99_收件箱，问题记入问题资产库，改深抽提示词/切块策略后重跑本批；
- 抽检结果写 `_meta/抽检记录.md`（日期、批次、抽几条、通过几条、失败原因）。

## 10. units 与 recipe / 检索打通

- `search_index.py units` 子命令：按 `--type`、`--topic`、`--confidence`、`--status` 查 units_index；
- **项目 recipe**（辅助层，跨工作流一键拉取）：recipe.yaml 可选 `units_type: [claim, procedure]`，项目拉取时附带相关单元类型；项目 recipe 与工作流主轴的关系是：工作流决定"笔记归到哪个环节"，recipe 决定"一次拉取哪些跨工作流笔记"；
- 笔记渲染：原子笔记的"核心结论"可引用同 chunk 的 units id，形成 笔记↔单元双链；
- units_index.json：按 type / topic / confidence 聚合，最小结构：
```json
{"total": 120,
 "by_type": {"claim": 60, "concept": 20, "procedure": 15, "relation": 10, "qa": 10, "open_question": 3, "conflict": 2},
 "by_topic": {"Codex剪口播": ["doc-x-claim-1", "..."]},
 "by_confidence": {"high": 80, "medium": 35, "low": 5},
 "no_evidence_high": [], "low_confidence": [], "conflicts": [], "errors": []}
```
